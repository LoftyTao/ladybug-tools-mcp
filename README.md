# Ladybug Tools MCP

[English](README.md) | [简体中文](README.zh-CN.md)

## Overview

Ladybug Tools MCP is an MCP service built with FastMCP for agent applications.
Through natural-language conversation, users can use the core capabilities of Ladybug Tools for common workflows including modeling, editing, querying, simulation, and data visualization, and can do so without depending on a CAD interface.

## User Groups

The original purpose of Ladybug Tools MCP is to turn design or technical concepts into concrete outputs quickly.
For example, when a professor explains “What is a Trombe wall?” in a building technology course, a student can open Codex voice mode during the lecture, and by the time the explanation is finished, Codex can already transform the concept into inspectable models and files, together with graphical workflow output.

For that reason, the main target users are students and teachers, followed by building professionals and senior engineers.
They may want an agent to take over some tedious work, while still keeping the final choice for most tasks in their own hands.
For users who do not know much about 3D software workflows, Ladybug Tools MCP can also serve as a way to experience the Ladybug Tools ecosystem.

## Core Concepts

Ladybug Tools MCP is different from Ladybug Tools as used inside Rhino / Grasshopper.
To use it well, it helps to understand several core concepts of this project, including MCP, agents, skills, tokens, Garden, and Flowerpot.

### Model Context Protocol

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) is an open standard used to connect external systems to agent applications.
For most users, Ladybug Tools provides a user interface for human interaction inside Rhino / Grasshopper.
Ladybug Tools MCP, by contrast, is a toolbox that an agent can call through natural language.
It packages the core capabilities of the Ladybug Tools Core SDK into a standardized set of tools and usage guidance, and exposes them through MCP so that agent applications can call them.

### Agent

An [Agent](https://openai.github.io/openai-agents-python/agents/) is a large language model with instructions and tools.
Ladybug Tools MCP is usually called as a toolset from inside an agent application.

### Agent Skills

[Skills](https://agentskills.io/home) are a practical way to turn prompt engineering into reusable operating guidance.
By summarizing domain knowledge and workflows in Markdown, they provide an “instruction manual” that helps an agent follow your intent more reliably.

### Tokens

Tokens are the unit used to calculate cost in agent applications.
Models differ in performance, speed, and token pricing, but I still recommend using the best and most cost-effective model you can reasonably access if you want a good Ladybug Tools MCP experience.

Long modeling and simulation workflows benefit from a large context window.
Usage and cost depend on the model, client, and task.

### Garden

A Garden is the local path used to store and manage everything generated by Ladybug Tools MCP. The main outputs inside it are tracked through Git.

Keeping models, weather files, simulation runs, and visualizations organized inside a Garden gives every tool a stable project context and predictable file layout.

### Flowerpot

Flowerpot is the intermediary layer used by Ladybug Tools MCP to exchange information with other non-agent interfaces.
For example, the Flowerpot components we developed for Ladybug Tools mainly act as relay plugins inside the ecosystem, with the goal of helping users complete the necessary manual work.

Because we want users to keep as much attention as possible on the interaction with the agent, instead of returning to manual production steps, we have not tried to build separate platform UIs for Ladybug Tools MCP. Instead, we recommend that you make good use of existing Ladybug Tools infrastructure and then pass data and information through Flowerpot.

## Quick Start

### Windows x86_64 Integrated Offline Installer

On Windows x86_64, the recommended distribution is the **Integrated Offline Installer** (`lbt-mcp-<ver>-win-x64-setup.exe`, e.g., `lbt-mcp-1.2.3-win-x64-setup.exe`) from [GitHub Releases](https://github.com/LoftyTao/ladybug-tools-mcp/releases).
It installs per-user without administrator rights and bundles Python `3.12`, `lbt-mcp`, Radiance `5.4 (2023-11-05)`, OpenStudio SDK `3.11.0`, unmodified EnergyPlus `25.2.0`, Ironbug `1.26.1` (with a self-contained `IronbugBridge.exe` requiring no external `.NET` runtime), LBT Measures, `pyHygroThermFEM-Fairyfly` + `gmsh` (THERM), `lbt-rune-viewer` (3D Viewer), and license notices. The offline installer includes Flowerpot component files for installation with `lbt-mcp flowerpot install`.

#### Optional URBANopt Offline Pack

District-scale Dragonfly URBANopt workflows use the separate **Optional URBANopt Offline Pack** (`lbt-mcp-<ver>-win-x64-urbanopt.lbtpack`, e.g., `lbt-mcp-1.2.3-win-x64-urbanopt.lbtpack`), which adds URBANopt CLI `1.4.0-rc1`, `OpenStudio/Ruby`, and runtime Gems.

- Place `lbt-mcp-<ver>-win-x64-urbanopt.lbtpack` beside `lbt-mcp-<ver>-win-x64-setup.exe` to detect and install it automatically during setup, or
- Install or remove it later with `lbt-mcp pack install` / `lbt-mcp pack remove`.

#### Default Paths and Non-ASCII / Space Path Handling

- **Default `<LBT_MCP_HOME>`**: `%LOCALAPPDATA%\lbt-mcp` when the Windows user profile path contains only ASCII characters and no spaces.
- **Automatic fallback**: `C:\lbt-mcp` when `%LOCALAPPDATA%` or the user profile path contains spaces or non-ASCII characters, because simulation engines such as Radiance, OpenStudio, and EnergyPlus expect ASCII, space-free runtime paths.
- **Custom paths**: If you choose a directory with spaces or non-ASCII characters in the installer, setup displays a warning and `lbt-mcp doctor` flags it.
- **Gardens workspace**: Defaults to `%USERPROFILE%\Gardens` and is always kept **outside** `<LBT_MCP_HOME>`, so models, weather files, simulation runs, and Git histories remain intact across upgrades and uninstalls. Spaces and Unicode characters inside Garden paths (via `LADYBUG_TOOLS_GARDENS_ROOT`) are supported.
- **Zero global environment pollution**: Setup never modifies system `PATH`, `RAYPATH`, or `~/.env_uo.bat`. Runtime paths are stored in `<LBT_MCP_HOME>\config\runtime.json` and synchronized into the bundled virtual environment's Ladybug Tools SDK `config.json` files.

### CLI Diagnostics, Runtime, Pack, and Flowerpot Commands

Run `<LBT_MCP_HOME>\bin\lbt-mcp.exe` (or `lbt-mcp` inside a Python environment) for server execution, diagnostics, runtime management, optional packs, and Flowerpot integration:

```text
lbt-mcp serve                                          # Start the stdio MCP server (default when no subcommand is given)
lbt-mcp status [--home <dir>] [--state <file>]         # Show active <LBT_MCP_HOME>, version, launcher, and Gardens root
lbt-mcp doctor [--home <dir>] [--smoke]                # Validate paths, SDK config sync, licenses, Rune viewer, and (--smoke) run engine probes
lbt-mcp runtime list|sync|set|reset                    # Inspect, sync to SDK config.json, override, or reset engine paths
lbt-mcp pack install <file.lbtpack> [--home <dir>]     # Verify SHA-256 digests and install an offline .lbtpack extension
lbt-mcp pack list [--home <dir>]                       # List installed extension packs
lbt-mcp pack remove <name> [--home <dir>]              # Remove pack-owned files and re-sync SDK configs
lbt-mcp flowerpot install [--grasshopper-dir <dir>]    # Install optional Rhino 8 / Grasshopper Flowerpot components
lbt-mcp flowerpot uninstall [--state <file>]           # Remove unmodified Flowerpot components
```

### Flowerpot and Platform Scope

Rhino 8 users on Windows can install Flowerpot with `lbt-mcp flowerpot install` after installing Ladybug Tools MCP. After restarting Grasshopper, the seven components are available by searching for `FP` or browsing the `Flowerpot` category (`FP Create Garden`, `FP Garden List`, `FP Honeybee Link`, `FP Dragonfly Link`, `FP Energy Properties Input`, `FP Radiance Properties Input`, and `FP Detail HVAC`). Rhino, Ladybug Tools for Grasshopper, and Ironbug are installed separately as required by the workflow. The [component guide](src/grasshopper_components/README.md) describes each component.

Garden version management requires Git on `PATH`. DES/Modelica requires GeoJSON Modelica Translator, ThermalNetwork, and the Modelica Buildings Library. OpenDSS requires an initialized Python environment for URBANopt. RNM and REopt require compatible local services.

Windows x86_64 is the primary integrated offline platform. Linux x86_64 and macOS Apple Silicon run the same core MCP and unit/contract checks in CI from PyPI or source packages; Flowerpot retains a Windows Rhino/Grasshopper boundary, while Fairyfly/THERM uses the bundled cross-platform `pyHygroThermFEM-Fairyfly` C++20 solver and headless Gmsh Q4 mesher across Windows, Linux, and macOS (no external LBNL THERM installation required). See [GitHub Releases](https://github.com/LoftyTao/ladybug-tools-mcp/releases) and the [distribution workflow](https://github.com/LoftyTao/ladybug-tools-mcp/actions/workflows/distribution.yml) for published release evidence.

### PyPI and Source Development Setup

On Linux, macOS, or custom Python 3.12 environments, you can install from PyPI with [uv](https://docs.astral.sh/uv/getting-started/installation/):

```text
uv venv --python 3.12
uv pip install --prerelease allow lbt-mcp==1.2.3
```

For source development and custom builds:

```text
git clone https://github.com/LoftyTao/ladybug-tools-mcp.git
cd ladybug-tools-mcp
uv venv --python 3.12
uv pip install --prerelease allow -e .
```

Source wheel builds support `LBT_MCP_REQUIRE_HYGROTHERM_NATIVE=1`, `LBT_MCP_REQUIRE_IRONBUG_BRIDGE=1`, and `LBT_MCP_REQUIRE_RUNE_VIEWER=1`; the Windows offline installer and corresponding-source bundle are built via `scripts/distribution/build_windows_bundle.py` and `scripts/distribution/build_corresponding_source.py`.

## Agent Client Configuration Guide

Configure your MCP client manually using the installed launcher and `serve` argument:

- **Command**: `<LBT_MCP_HOME>\bin\lbt-mcp.exe`
- **Args**: `["serve"]`
- **Environment**:
  - `LADYBUG_TOOLS_GARDENS_ROOT`: your Gardens root directory (default `%USERPROFILE%\Gardens`, kept outside `<LBT_MCP_HOME>`)
  - `LADYBUG_TOOLS_MCP_HOME` (optional): explicit `<LBT_MCP_HOME>` path (`lbt-mcp.exe` auto-detects `<LBT_MCP_HOME>` from its parent directory when omitted)

> **Tip**: Run `<LBT_MCP_HOME>\bin\lbt-mcp.exe status` to print the resolved absolute paths for your machine. Most MCP clients do not expand `%LOCALAPPDATA%` or `%USERPROFILE%`, so replace `<LBT_MCP_HOME>` (e.g., `C:\lbt-mcp` or `C:\Users\<user>\AppData\Local\lbt-mcp`) and `<GARDENS_ROOT>` (e.g., `C:\Users\<user>\Gardens`) with actual absolute paths (escaped with `\\` inside JSON strings, or single-quoted `'...'` literal strings in TOML).

### Codex (`~/.codex/config.toml`)

Merge into `$CODEX_HOME/config.toml` (default `~/.codex/config.toml`):

```toml
[mcp_servers.lbt-mcp]
command = '<LBT_MCP_HOME>\bin\lbt-mcp.exe'
args = ["serve"]
startup_timeout_sec = 60
required = true

[mcp_servers.lbt-mcp.env]
LADYBUG_TOOLS_GARDENS_ROOT = '<GARDENS_ROOT>'
# Optional:
# LADYBUG_TOOLS_MCP_HOME = '<LBT_MCP_HOME>'
```

### Claude Code (`.mcp.json` / `claude mcp add-json`)

Project `.mcp.json`:

```json
{
  "mcpServers": {
    "lbt-mcp": {
      "type": "stdio",
      "command": "<LBT_MCP_HOME>\\bin\\lbt-mcp.exe",
      "args": ["serve"],
      "env": {
        "LADYBUG_TOOLS_GARDENS_ROOT": "<GARDENS_ROOT>"
      }
    }
  }
}
```

Or register at user scope via CLI (pass only the inner server object; do not replace `~/.claude.json`):

```text
claude mcp add-json --scope user lbt-mcp '{"type":"stdio","command":"<LBT_MCP_HOME>\\bin\\lbt-mcp.exe","args":["serve"],"env":{"LADYBUG_TOOLS_GARDENS_ROOT":"<GARDENS_ROOT>"}}'
```

For any standard stdio MCP client, configure `command`, `args`, and `env` as follows (omit `LADYBUG_TOOLS_MCP_HOME` if you rely on `<LBT_MCP_HOME>\bin\lbt-mcp.exe` auto-detection):

  }

```text

```

## Web View Mode

Web View Mode connects your Garden directly to the native GPU-accelerated Rune 3D viewer (`lbt-rune-viewer`) for live modeling, inspection, and bidirectional spatial annotation.
While an agent creates, edits, or validates Honeybee or Dragonfly models, `lbt-rune-viewer` renders the live Garden geometry with native wgpu rendering, CAD camera controls, section cuts, attribute coloring, and 3D object picking.

### Enable

Ask the agent to enable Web View Mode before modeling or editing:

```text
Enable Web View Mode for this Garden, then create or edit the Honeybee model.
```

Through MCP Code Mode, the agent calls:

```text
GD_Web_View_Start_Mode(garden_root, name="...", open_window=True)
```

Starting the mode initializes the atomic Garden protocol files under `<garden>/tmp/web_view/` (`session.json`, `present.json`, and `interaction_state.json`), seeds `present.json` from the Garden's base Honeybee or Dragonfly model (converting Dragonfly buildings into `tmp/web_view/models/` for preview), and launches `lbt-rune-viewer` when `open_window=True` and a GUI display is available (pass `open_window=False` for headless or protocol-only sessions).

### Direct, Inspect, and Capture

- `GD_Web_View_Present`: direct the viewport (`view_type`, `color_by`, `highlight_targets`, `isolation_mode`, `validation_issues`, `camera`, `section`, `callouts`, `title`, and `note`).
- `GD_Web_View_Get_Context`: read user-selected targets, 3D spatial annotation pins, viewport camera state, and pending intents from `interaction_state.json`, and optionally resolve pins atomically.
- `GD_Web_View_Capture`: capture a PNG verification screenshot under `<garden>/tmp/web_view/captures/` via the live `lbt-rune-viewer` handshake first, headless `lbt-rune-viewer --snap` second, or offscreen VTK fallback third.

### Close

Ask the agent to stop Web View Mode, or call:

```text
GD_Web_View_Stop_Mode(garden_root)
```

This disables future automatic `present.json` updates and stops any tracked `lbt-rune-viewer` process.
Protocol history under `tmp/web_view/` is preserved.

### Difference From Ordinary Mode

In ordinary mode, modeling tools write Garden files and return compact targets, summaries, and receipts without launching `lbt-rune-viewer` or writing `tmp/web_view/present.json` after edits.

In Web View Mode, significant Honeybee, `HB_Validate_Model`, and Dragonfly operations in Code Mode automatically flush coalesced updates to `<garden>/tmp/web_view/present.json`, and `lbt-rune-viewer` reloads changed geometry in place while keeping your current camera pose.
These session files are local preview state, not formal user-requested Garden artifacts.
If you need a durable reusable export (`html`, `svg`, `png`, `vtkjs`, `vtk`, `vtp`, `vsf`, or `pkl`), ask the agent to export a VisualizationSet with `LB_Export_Visualization_Set`.

## First Use

After configuring your MCP client according to the [Agent Client Configuration Guide](#agent-client-configuration-guide) (pointing `command` to `<LBT_MCP_HOME>\bin\lbt-mcp.exe` with `args = ["serve"]`), restart the client, start a new thread, and describe your Garden or modeling task directly.

Choosing a capable model with a large context window helps multi-step modeling and simulation workflows run more reliably.

## Workflow Examples

In our cross-testing set, we have successfully made agent applications complete the following kinds of work.
The stability and token cost of these workflows have become relatively steady, and I believe they are a good place to begin learning.

### Build a small model from a blank project

- Create a new Garden.
- Create a Honeybee Model.
- Create one or two Rooms.
- Add windows, doors, and shades to exterior walls.
- Check whether the model has missing faces, broken adjacencies, or boundary-condition issues.

### Continue editing an existing model

- Find the specified room, wall, window, or door.
- Modify the location, dimensions, and construction of windows.
- Add low-U-value windows, heavy wall constructions, occupant loads, and equipment loads.
- Assign program types, setpoints, and a simple HVAC system to rooms.
- Re-check the model after editing.

### Building performance simulation workflow

- Search for and download the EPW weather file for a specified city.
- Save the weather file into the Garden.
- Start an Energy simulation.
- Read EUI, error information, and some hourly results.
- Export the results as monthly charts, hourly charts, or HTML pages.

### Prepare reusable Energy resources

- Create schedules, program types, construction sets, setpoints, and HVAC templates.
- Save them into the Garden Properties Library.
- Search for and reuse these resources in later models.
- For incomplete sources, record only what can be determined and do not invent material layers or window parameters.

### Author custom HVAC with Ironbug

- Create Ironbug DetailedHVAC objects for coils, fans, pumps, boilers, chillers, terminals, plant loops, air loops, setpoint managers, and output requests.
- Assemble source-backed custom HVAC systems such as PTAC, PTHP, FCU, DOAS, VAV, VRF, boiler reheat, chiller plant, and condenser-water loop cases.
- Link Ironbug ThermalZone objects to Honeybee or Dragonfly rooms, then apply the DetailedHVAC model before running the standard Energy simulation workflow.
- Use the Ironbug workflow when an HVAC Template is too coarse and you need object-level loop topology, child components, and OpenStudio / EnergyPlus-facing equipment intent.

### Do basic Radiance work

- Create skies, WEA files, sky matrices, sensor grids, and views.
- Assign Radiance modifiers to model objects.
- Start grid or view simulations.
- Read HDR, falsecolor, GIF, or annual daylight metrics.
- Convert the results into inspectable visualization sets.

### Connect Grasshopper and the agent

- Use Flowerpot components in Grasshopper to hand over the current model or project context.
- Let the agent continue modeling, editing, saving, and validating in the Garden.
- Let the Grasshopper side continue to handle manual selection, preview, and the necessary manual operations.
- This is suitable for a workflow where geometry is handled in the interface and organization plus long-chain tool use is handled by the agent.

### Preserve and restore project state

- Create a Garden Version before important operations.
- Try modifying the model or simulation resources.
- If the result is unsatisfactory, restore to the earlier version.
- After restoration, continue exporting HTML / SVG and other inspection outputs.

## How to Contribute

Because this project is built to a very large extent through agent-assisted development, I do not reject contributions made with agent applications.
However, there are several principles that need to be followed so that the project does not grow in an uncontrolled way.

- [Ladybug Tools Core SDK](https://discourse.ladybug.tools/pub/ladybug-tools-core-sdk-documentation) is the core of all MCP tools in this project.
If the tool you want to add is not within the scope of the SDK, then this project should not be the place for the follow-up implementation.
In that case, it is more appropriate to contribute directly to the Ladybug Tools project itself.
- All new tool development should first go through an open GitHub Issue discussion, and the discussion content and development plan should be led by humans.
- Only write code that solves the current problem, avoiding unnecessary complexity or speculative abstractions.
- Better to have too few tools than too many; do not add entities unless they are truly necessary.
- If these principles can be followed, I would be very happy for you to join this community-driven maintainer group.
